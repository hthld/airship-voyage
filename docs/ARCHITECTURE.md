# Архитектура Airship Voyage — рабочие заметки

Документ фиксирует технические решения, принятые при развёртывании проекта, и предложения по открытым вопросам ТЗ (раздел 30).
Всё, что помечено «предложение», не утверждено.

## 1. Слои

```
┌──────────────────────────────────────────────┐
│ client/  — рендер, LOD, звук, интерфейс       │  только клиент
├──────────────────────────────────────────────┤
│ игровые подсистемы (blueprint, assembly,      │  NeoForge API,
│ gas, control, damage, …) + network            │  сервер — источник истины
├──────────────────────────────────────────────┤
│ core/  — физика и логика без Minecraft        │  чистая Java 21,
│ (physics, позже structure, damage-модель)     │  unit-тесты
└──────────────────────────────────────────────┘
```

`core` не импортирует `net.minecraft.*` и `net.neoforged.*`. Это позволяет:
проверять баланс без запуска игры, переиспользовать код при смене версии Minecraft
(открытый вопрос №2) и гонять «что если» по цифрам исторических кораблей.

## 2. Единицы и оси

- СИ везде: метры, килограммы, секунды, ньютоны, кельвины, паскали, моли.
- Горизонталь: 1 блок = 1 м (ТЗ 3.1).
- Вертикаль атмосферы: `AltitudeMapper` с настройкой `physics.altitudeMetersPerBlock`.
  При значении ≠ 1 высота для расчёта газа растягивается, а геометрия корабля — нет.
  **Внимание:** вертикальная скорость в ядре — в метрах физической высоты; при переводе в блоки
  её нужно делить на тот же коэффициент. Решение по масштабу (ТЗ 8.8) — после прототипа.
- Локальные оси корпуса: X — к носу, Y — вверх, Z — к правому борту, начало — центр корпуса.

## 3. Газ (реализовано)

Мягкая камера при давлении окружающего воздуха: `V = min(nRT/P, V_cap)`.
Подъёмная сила = `ρ_air·g·V − m_gas·g`. Ниже высоты давления подъёмная сила постоянна
(газ расширяется ровно настолько, насколько падает плотность воздуха), выше — автоклапан
стравливает излишек. Это даёт реалистичное поведение без «сброса газа на каждый блок высоты» (ТЗ 7.4).

## 4. Предложение по физическому движку (открытый вопрос №7)

**Собственный интегратор твёрдого тела в `core`**, без внешнего физического движка:

- Корабль во время полёта — одно твёрдое тело (ТЗ 16.8, 22.5): позиция, кватернион ориентации,
  линейная и угловая скорость, тензор инерции, собранный из `PointMass` и камер.
- Силы: аэростатика (уже есть), тяга двигателей, аэродинамическое сопротивление по осям,
  моменты рулей (∝ квадрату воздушной скорости — ТЗ 8.5), ветер, присоединённые массы.
- Интегрирование на сервере с фиксированным шагом (20 тиков/с, при необходимости — подшаги).
- Столкновения: AABB корабля → блоки мира в нём → упрощённые формы (OBB/капсулы на секцию) → контакт →
  событие в систему повреждений (ТЗ 22.6).

Почему не готовый движок (Bullet/JBullet, Rapier через JNI и т.п.): кораблей мало, тел мало,
а главная сложность — не решатель контактов, а интеграция с блоками Minecraft и движением игрока.
Внешний движок это не решает, но добавляет нативные зависимости. Пересмотреть, если на этапе
крушений (фаза 9) понадобится много одновременных тел.

## 5. Предложение по сущности корабля

- Корабль в мире — одна серверная сущность (`Entity`) с собственными данными в `SavedData`
  (уникальный ID, полное состояние из ТЗ 22.3), чтобы состояние не зависело от загрузки чанков.
- Сущность сама принудительно держит загруженными чанки под собой, пока на борту есть игрок
  или корабль в полёте; иначе симуляция замораживается (ТЗ 22.9).
- Визуальная модель — набор частей, рендерящихся в локальных координатах; коллизия — отдельные
  упрощённые формы на каждую часть.

## 6. Игрок на движущемся корабле (главный риск №2)

Предложение: при контакте с полом корабля игрок «привязывается» к кораблю, и его позиция хранится
в локальных координатах. Каждый тик: локальная позиция → мировая через трансформацию корабля,
поверх — собственное движение игрока. При прыжке игрок наследует скорость точки корпуса
под ногами. Скорее всего, потребуются mixin'ы в обработку движения/коллизий игрока —
это нужно проверить первым делом, до любых больших моделей.

## 7. Блоки на борту (риск №3)

Отдельная локальная сетка блоков (палитра + массив, как в секциях чанков) внутри свободных зон.
На первом этапе — белый список: сундуки, бочки, верстаки, печи, кровати, декоративные блоки.
Взаимодействие — через собственный адаптер (открыть контейнер блока из локальной сетки).

## 8. Формат 3D-ассетов (открытый вопрос №6)

Предложение: модели в Blockbench → JSON/OBJ для рендера, отдельный простой JSON с
коллизионными формами, массами, точками монтажа и разрушаемыми секциями.
Чертёж корабля = список деталей с локальными позициями + зависимости «что должно стоять до».

## 9. Сущность-корабль (реализовано, шаг 1 прототипа)

- `AirshipEntity` — одна сущность на корабль. Позиция сущности = начало локальных координат корпуса.
  Источник истины — `core.rigid.RigidBody` на сервере; клиент физику не считает.
- Синхронизация: позиция — обычный трекинг сущностей Minecraft (каждый тик, дальность 16 чанков),
  ориентация (кватернион) и ID типа корабля — `SynchedEntityData`. Клиент сглаживает позицию и
  ориентацию (slerp) за 3 тика и интерполирует внутри кадра.
- Коробка сущности (`makeBoundingBox`) — описанный AABB всех коллизионных коробок в текущей ориентации.
  Она нужна для отсечения рендера и поиска; **как коллизия она не используется** (`canBeCollidedWith = false`,
  `isPickable = false`): у каркаса внутри пустота, и единая коробка стала бы невидимой стеной и перехватывала
  бы клики по блокам. Настоящая коллизия — по OBB деталей, шаг 2.
- Сохранение: тип, ориентация, линейная и угловая скорость (NBT сущности). `SavedData` с UUID корабля
  понадобится, когда появятся строительство и выгрузка чанков с игроками на борту (ТЗ 22.9).
- Отладка: `/airship …` (debug/AirshipCommands), проверки — `debug/AirshipGameTests` (`runGameTestServer`).
- Временный рендер рисует каждую коллизионную коробку текстурированным параллелепипедом (текстуры тайлятся
  по 1 м). Когда появятся модели (разд. 8), коробки останутся отладочным режимом.

### Найдено при реализации

- Явный шаг Эйлера для ориентации непригоден для дирижабля: моменты инерции по крену и курсу различаются
  в десятки раз, и свободное вращение за минуту «накачивало» энергию в 20 раз. Теперь хранится угловой
  момент, ориентация интегрируется RK4 — дрейф энергии < 0,1 % за минуту.
- Сопротивление голой решётки мало (пористость ≈ 0,85): каркас-прототип после толчка идёт по инерции
  десятки секунд. С обшивкой (фаза 5) сопротивление вырастет в разы — это реалистично.

## 10. Игрок на движущемся корабле (реализовано, шаг 2 прототипа)

**Столкновения.** Mixin в `Entity.collide` (RETURN): после ванильной обработки блоков смещение обрезается
деталями ближайших кораблей (`collision/ShipCollisions` → `core/collision/HullCollider`). Ключевая идея:
в локальных осях корпуса детали — обычные осевые коробки, даже если корабль повёрнут. Коробка сущности
переводится в оси корпуса (описанная осевая), смещение обрезается по осям как в ванили (Y, затем большая
из X/Z), результат переводится обратно. Флаги «на земле», «упёрся», урон от падения Minecraft считает сам.

**Кто кого считает.** Свой игрок — на клиенте (клиент Minecraft сам двигает своего игрока); мобы и
предметы — на сервере; серверный игрок кораблями не обрезается. Причина: сервер перепроверяет движение
игрока, а корабль на клиенте отстаёт на сеть и сглаживание — двойная проверка давала бы откаты
(«moved wrongly»). Цена — меньше защиты от читов на корабле; вернуться к этому в фазе 12.

**Перенос.** Касание «сверху» запоминается (сущность → корабль, время). Каждый тик корабля стоящие
переносятся жёстко с корпусом (`HullCollider.carry`) и поворачиваются на изменение курса. Подпрыгнувший
переносится, пока он внутри габарита корабля (до 40 тиков) — корабль не уезжает из-под ног (ТЗ 12.3).
Покинувший корабль получает скорость палубы.

**Наклон.** При наклоне корпуса описанная коробка вертикального игрока в осях корпуса шире и тонет в палубе
на сантиметры; неглубокое (до 0,25 м) погружение сверху выталкивается. До 30° наклона сила тяжести действует
по нормали к палубе (сцепление, ТЗ 12.4), круче — скольжение. Оба эффекта найдены игровыми тестами.

**Анти-полёт.** Mixin в `ServerGamePacketListenerImpl.noBlocksAround`: игрок у деталей корабля не считается
«висящим в воздухе» (иначе выделенный сервер кикает через ~4 с).

**Реестр кораблей.** Поиск сущностей Minecraft не годится — корабль хранится в секции чанка по центру,
а игрок у кормы 245-метрового корабля в сотне блоков от неё. `ShipRegistry` держит загруженные корабли по мирам.

**GameTest.** Шаблон `ship_dock` 28×22×28 (раньше был `ship_bay` 17×14×17 — удалён вместе с `empty`):
каждый тест удаляет сущности в своей зоне при старте, и корабль, задевающий соседнюю зону, исчезал.
Фазы тестов отсчитываются по тикам корабля, а не по часам теста.

### Ограничения шага 2 (осознанные)

- Нет «ступеньки» на детали корабля (подъём на 0,5 м без прыжка) — вход на настил прыжком.
- Корабль не толкает сущности, в которые въезжает боком — проходит сквозь (пункт 9 прототипа).
- Детали с поворотом внутри корпуса (не осевые) пока учитываются по описанной коробке.
- Клиентская часть (свой игрок) автотестами не покрыта — GameTest работает только на сервере.

## 11. Подъёмная сила, повреждение камеры, земля (реализовано, шаги 3–4 прототипа)

**FlightModel** (`core/flight`) — полёт как целое, без Minecraft. За тик: газ (утечки, автоклапаны,
перегрев), пересборка массы при изменении > 50 г, затем 1 или 8 подшагов (8 — если рядом твёрдые блоки):
вес в центре масс; архимедова сила каждой камеры в центре газа (газ собирается у верха неполного мешка);
сопротивление; контакт; шаг `RigidBody`. Мир — через `Environment`/`ContactQuery`, в игре это
`physics/WorldEnvironment`.

**Камеры в чертеже** — `CellSlot` (отсек, коэффициент заполнения 0,9, масса оболочки 0,2 кг/м²).
**Присоединённая масса** — в `RigidBody` по осям корпуса: (0,1; 0,9; 0,9) × масса воздуха, вытесненного
камерами. У прототипа поперёк оси это ≈ 1,7 т при собственной массе 1,5 т.

**Контакт с миром.** Точки на рёбрах деталей через ≤ 1 м (у прототипа ≈ 1000). Вошедшая в блок точка
получает пружину с демпфером по нормали и трение (Кулон, сглаженный вязким около нуля). Суммарная
жёсткость задана на кг эффективной вертикальной массы (собственная + присоединённая) и делится между
касающимися точками: осадка = вес / (400·(m + m_прис)) при любом числе точек, явный интегратор устойчив.
У каркаса без камер это g/400 ≈ 2,5 см, у прототипа с пустыми камерами ≈ 1,1 см (сверено игровым тестом
в шаге 5: 13 734 Н / (400 · 3144 кг) = 1,09 см, измерено 1,09). Глубина ограничена 0,25 м — корабль, оказавшийся в земле,
выдавливается со скоростью ≤ 3,6 м/с, а не выстреливает. Нормаль блока берётся только с «открытых»
граней (сосед не полный блок) — точка в земле выталкивается вверх, а не вбок.

**Поведение (проверено тестами и сверено с ручным расчётом):** уравновешивание прототипа при 77,5 %
наполнения (масса 1500 кг); уравновешенный висит на любой высоте ниже высоты давления; наполнение 95 %
у земли → высота давления ≈ 450 м, дальше стравливание и подъём до ≈ 2,6 км, где корабль проскакивает
равновесие, тяжелеет и медленно снижается (как настоящий); утечка 1 %/с в носовой камере → −10° за 30 с;
крен: период ≈ 20 с, раскачка затухает; при посадке сила контакта = весу.

**Найдено при реализации.** Массы ферм в шаге 1 были завышены вчетверо (оценка 30–40 кг/м против
2,5–5 кг/м у цеппелинов) — исправлено. Маленький каркас 13×7×7 газ не поднимет даже с правильными
массами: подъёмная сила растёт как объём, масса каркаса — примерно как поверхность. Поэтому летающий
прототип крупнее.

**Стоимость.** ≈ 0,3–0,4 мс на тик для прототипа (ядро, без учёта обращений к блокам). Для LZ 129
понадобятся: точки контакта только с нижней стороны корпуса и только у блоков из быстрой отсечки
по секциям, а не по всему габариту; кэш состояний блоков на тик.

### Ограничения (осознанные)

- Масса стоящих на борту игроков и мобов не учитывается (ТЗ 8.3) — следующий кандидат.
- Газ всегда при температуре воздуха (+ перегрев, который пока никто не задаёт); ветер нулевой.
- Нет двигателей и рулей (фаза 3 по ТЗ 26) — горизонтально корабль двигают отладочные команды.
- Удар о землю не повреждает каркас — `StepReport.maxImpactSpeed` уже считается для будущей системы повреждений.
- Корабль не толкает сущности, в которые въезжает; блоки мира не ломает.

## 12. Строительство (реализовано, шаг 5 — фаза 1, пункты 1–2 прототипа)

**Ядро (`core/assembly`).** `AssemblyPlan` — монтажный план чертежа: каждая деталь и камера `ShipLayout` —
монтажная точка с предметом, этапом (ТЗ 5.4) и явным списком опор «что должно стоять до». Опоры заданы вручную,
а не выведены из геометрии: 20-метровая ферма касается и одного кольца, но держаться на нём не может. Тест сверяет,
что каждая опора физически примыкает к детали (зазор ≤ 15 см), и что проверка чувствительна (киль в 2 м под
мешком опорой не считается). План проверяется при создании: все детали покрыты, ссылки существуют, циклов нет.
Детали без опор стоят на стапеле — их нижние точки контакта и есть стапельные опоры площадки.
`ConstructionState` — прогресс: установка с отказами (не тот предмет, уже стоит, нет опор + список недостающих).
`AssemblyTargeting` — луч взгляда в осях корпуса против коробок неустановленных точек для предмета в руке
(`OrientedBox.rayHit`, метод плит); одно и то же считают клиент (подсветка) и сервер (установка).
`SiteCheck` — размещение и проверка площадки (ТЗ 4.2): низ корпуса на верхней грани блока, на который смотрят,
центр над ним, курс кратен 90°; проверка — высота мира, пересечение с другими кораблями, твёрдый блок под
каждой стапельной опорой (у прототипа 39 столбцов под тремя кольцами), свободный объём габарита.

**Игра.** Стройка — та же `AirshipEntity` в режиме «на стапеле»: физика заморожена, коллизия и рендер — только
установленные детали (`hullShapes()`, `visibleParts()`), прогресс — в NBT («Construction») и в синхронизируемых
данных. Поэтому хождение по собранному (ТЗ 5.5) работает без нового кода, а спуск (`launch()`) — это снятие режима:
тот же корабль начинает летать, мешки пустые, корабль лежит на опорах.
`BlueprintTableBlock` выдаёт чертёж и сводку (окна выбора нет — модель одна). `BlueprintItem`: ПКМ — разместить
проект, Shift+ПКМ — ход работ или спуск. `ShipPartItem` (кольцо, киль, ферма, мешок): ПКМ → `ConstructionSites.tryInstall`
проверяет то, что требует мира, — блок между глазами и точкой (ТЗ 5.2 «перекрыт доступ»), блоки и живые сущности
в объёме детали; при успехе предмет расходуется (не в творческом), звук. Клиент: `BuildPreview` рисует контур
проекта (зелёный/красный, проблемный блок, нос), `AirshipRenderer` — «призраки» неустановленных деталей:
бледные в 8 м от игрока, голубые — куда можно поставить деталь из руки, зелёный/красный — выбранная взглядом.
Команды: `/airship build complete|launch`; команды полёта на стройку не действуют.

**Проверено.** Unit: план, порядок установки, выбор взглядом (в т.ч. повёрнутый корабль и «сквозь кольцо — мимо»),
площадка с числами ручного расчёта (габарит 90,25…110,75 при щелчке по x = 100; блок x = 90 мешает, x = 89 — нет;
верх ровно на y = 77 не мешает — нужен допуск на границе блоков). Игровые тесты: площадка в доке (помеха, яма под
кольцом, яма между кольцами), монтаж через настоящий предмет у игрока-заглушки (опоры, досягаемость, камень на линии
взгляда, камень и стойка в объёме киля, расход предметов), стойка проваливается сквозь пустое место киля и стоит на
установленном, сохранение стройки, стройка неподвижна, спуск: осадка 1,1 см, с 95 % газа — подъём 2,1 м за 2 с.

### Ограничения (осознанные)

- Стол — без окна выбора моделей (одна модель); чертёж — один предмет на тип корабля.
- Курс проекта только по сторонам света; площадка — один уровень под всеми кольцами.
- Пересечение проектов проверяется только с загруженными кораблями (`ShipRegistry`); `SavedData` с реестром
  кораблей появится вместе с выгрузкой чанков (ТЗ 22.9).
- Детали нельзя снять обратно (только `/airship remove` всей стройки); нет стапельных опор/лесов как объектов.
- Газ после спуска — командой; заправка (ТЗ 7.3, этап IX) — позже.
- Масса игроков на борту по-прежнему не учитывается.

## 13. План следующего шага (предложение) — двигатели и управление (фаза 3)

1. Двигатель как деталь плана (гондола с винтом): тяга в точке крепления по оси корпуса, ступени телеграфа
   (стоп / малый / средний / полный, задний), расход топлива — позже (ТЗ 8.4).
2. Рули высоты и направления: момент ∝ квадрату воздушной скорости (ТЗ 8.5), без скорости руль не действует.
3. Пост управления на борту (блок-штурвал на настиле киля): игрок у поста задаёт телеграф и рули; сброс
   балласта и клапаны газа — оттуда же (ТЗ 9.1–9.2).
4. Масса игроков и мобов на палубе (ТЗ 8.3) — через уже существующие контакты переноса.
5. Тесты: разгон до установившейся скорости (тяга = сопротивление), разворот рулём только на ходу, дифферент
   от людей на носу.
