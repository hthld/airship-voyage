# Архитектура Airship Voyage — рабочие заметки

Документ описывает текущее устройство мода: слои, подсистемы по шагам, что найдено при реализации, ограничения.
Решения и их причины (утверждённые и предложения) — `docs/DECISIONS.md`; задачи — `docs/TASKS.md`;
история сессий — `docs/sessions/`. Разделы 4–8 — ранние предложения по открытым вопросам ТЗ (раздел 30);
их статус — в `docs/DECISIONS.md`.

## 1. Слои

```
┌──────────────────────────────────────────────┐
│ client/  — рендер, LOD, звук, интерфейс       │  только клиент
├──────────────────────────────────────────────┤
│ игровые подсистемы (blueprint, assembly,      │  NeoForge API,
│ gas, control, damage, …) + network            │  сервер — источник истины
├──────────────────────────────────────────────┤
│ core/  — физика и логика без Minecraft        │  чистая Java 21,
│ (physics, позже structure, damage-модель)     │  unit-тесты
└──────────────────────────────────────────────┘
```

`core` не импортирует `net.minecraft.*` и `net.neoforged.*`. Это позволяет:
проверять баланс без запуска игры, переиспользовать код при смене версии Minecraft
(открытый вопрос №2) и гонять «что если» по цифрам исторических кораблей.

## 2. Единицы и оси

- СИ везде: метры, килограммы, секунды, ньютоны, кельвины, паскали, моли.
- Горизонталь: 1 блок = 1 м (ТЗ 3.1).
- Вертикаль атмосферы: `AltitudeMapper` с настройкой `physics.altitudeMetersPerBlock`.
  При значении ≠ 1 высота для расчёта газа растягивается, а геометрия корабля — нет.
  **Внимание:** вертикальная скорость в ядре — в метрах физической высоты; при переводе в блоки
  её нужно делить на тот же коэффициент. Решение по масштабу (ТЗ 8.8) — после прототипа.
- Локальные оси корпуса: X — к носу, Y — вверх, Z — к правому борту, начало — центр корпуса.

## 3. Газ (реализовано)

Мягкая камера при давлении окружающего воздуха: `V = min(nRT/P, V_cap)`.
Подъёмная сила = `ρ_air·g·V − m_gas·g`. Ниже высоты давления подъёмная сила постоянна
(газ расширяется ровно настолько, насколько падает плотность воздуха), выше — автоклапан
стравливает излишек. Это даёт реалистичное поведение без «сброса газа на каждый блок высоты» (ТЗ 7.4).

## 4. Предложение по физическому движку (открытый вопрос №7)

**Собственный интегратор твёрдого тела в `core`**, без внешнего физического движка:

- Корабль во время полёта — одно твёрдое тело (ТЗ 16.8, 22.5): позиция, кватернион ориентации,
  линейная и угловая скорость, тензор инерции, собранный из `PointMass` и камер.
- Силы: аэростатика (уже есть), тяга двигателей, аэродинамическое сопротивление по осям,
  моменты рулей (∝ квадрату воздушной скорости — ТЗ 8.5), ветер, присоединённые массы.
- Интегрирование на сервере с фиксированным шагом (20 тиков/с, при необходимости — подшаги).
- Столкновения: AABB корабля → блоки мира в нём → упрощённые формы (OBB/капсулы на секцию) → контакт →
  событие в систему повреждений (ТЗ 22.6).

Почему не готовый движок (Bullet/JBullet, Rapier через JNI и т.п.): кораблей мало, тел мало,
а главная сложность — не решатель контактов, а интеграция с блоками Minecraft и движением игрока.
Внешний движок это не решает, но добавляет нативные зависимости. Пересмотреть, если на этапе
крушений (фаза 9) понадобится много одновременных тел.

## 5. Предложение по сущности корабля

- Корабль в мире — одна серверная сущность (`Entity`) с собственными данными в `SavedData`
  (уникальный ID, полное состояние из ТЗ 22.3), чтобы состояние не зависело от загрузки чанков.
- Сущность сама принудительно держит загруженными чанки под собой, пока на борту есть игрок
  или корабль в полёте; иначе симуляция замораживается (ТЗ 22.9).
- Визуальная модель — набор частей, рендерящихся в локальных координатах; коллизия — отдельные
  упрощённые формы на каждую часть.

## 6. Игрок на движущемся корабле (главный риск №2)

Предложение: при контакте с полом корабля игрок «привязывается» к кораблю, и его позиция хранится
в локальных координатах. Каждый тик: локальная позиция → мировая через трансформацию корабля,
поверх — собственное движение игрока. При прыжке игрок наследует скорость точки корпуса
под ногами. Скорее всего, потребуются mixin'ы в обработку движения/коллизий игрока —
это нужно проверить первым делом, до любых больших моделей.

## 7. Блоки на борту (риск №3)

Отдельная локальная сетка блоков (палитра + массив, как в секциях чанков) внутри свободных зон.
На первом этапе — белый список: сундуки, бочки, верстаки, печи, кровати, декоративные блоки.
Взаимодействие — через собственный адаптер (открыть контейнер блока из локальной сетки).

## 8. Формат 3D-ассетов (открытый вопрос №6)

Предложение: модели в Blockbench → JSON/OBJ для рендера, отдельный простой JSON с
коллизионными формами, массами, точками монтажа и разрушаемыми секциями.
Чертёж корабля = список деталей с локальными позициями + зависимости «что должно стоять до».

## 9. Сущность-корабль (реализовано, шаг 1 прототипа)

- `AirshipEntity` — одна сущность на корабль. Позиция сущности = начало локальных координат корпуса.
  Источник истины — `core.rigid.RigidBody` на сервере; клиент физику не считает.
- Синхронизация: позиция — обычный трекинг сущностей Minecraft (каждый тик, дальность 16 чанков),
  ориентация (кватернион) и ID типа корабля — `SynchedEntityData`. Клиент сглаживает позицию и
  ориентацию (slerp) за 3 тика и интерполирует внутри кадра.
- Коробка сущности (`makeBoundingBox`) — описанный AABB всех коллизионных коробок в текущей ориентации.
  Она нужна для отсечения рендера и поиска; **как коллизия она не используется** (`canBeCollidedWith = false`,
  `isPickable = false`): у каркаса внутри пустота, и единая коробка стала бы невидимой стеной и перехватывала
  бы клики по блокам. Настоящая коллизия — по OBB деталей, шаг 2.
- Сохранение: тип, ориентация, линейная и угловая скорость (NBT сущности). `SavedData` с UUID корабля
  понадобится, когда появятся строительство и выгрузка чанков с игроками на борту (ТЗ 22.9).
- Отладка: `/airship …` (debug/AirshipCommands), проверки — `debug/AirshipGameTests` (`runGameTestServer`).
- Временный рендер рисует каждую коллизионную коробку текстурированным параллелепипедом (текстуры тайлятся
  по 1 м). Когда появятся модели (разд. 8), коробки останутся отладочным режимом.

### Найдено при реализации

- Явный шаг Эйлера для ориентации непригоден для дирижабля: моменты инерции по крену и курсу различаются
  в десятки раз, и свободное вращение за минуту «накачивало» энергию в 20 раз. Теперь хранится угловой
  момент, ориентация интегрируется RK4 — дрейф энергии < 0,1 % за минуту.
- Сопротивление голой решётки мало (пористость ≈ 0,85): каркас-прототип после толчка идёт по инерции
  десятки секунд. С обшивкой (фаза 5) сопротивление вырастет в разы — это реалистично.

## 10. Игрок на движущемся корабле (реализовано, шаг 2 прототипа)

**Столкновения.** Mixin в `Entity.collide` (RETURN): после ванильной обработки блоков смещение обрезается
деталями ближайших кораблей (`collision/ShipCollisions` → `core/collision/HullCollider`). Ключевая идея:
в локальных осях корпуса детали — обычные осевые коробки, даже если корабль повёрнут. Коробка сущности
переводится в оси корпуса (описанная осевая), смещение обрезается по осям как в ванили (Y, затем большая
из X/Z), результат переводится обратно. Флаги «на земле», «упёрся», урон от падения Minecraft считает сам.

**Кто кого считает.** Свой игрок — на клиенте (клиент Minecraft сам двигает своего игрока); мобы и
предметы — на сервере; серверный игрок кораблями не обрезается. Причина: сервер перепроверяет движение
игрока, а корабль на клиенте отстаёт на сеть и сглаживание — двойная проверка давала бы откаты
(«moved wrongly»). Цена — меньше защиты от читов на корабле; вернуться к этому в фазе 12.

**Перенос.** Касание «сверху» запоминается (сущность → корабль, время). Каждый тик корабля стоящие
переносятся жёстко с корпусом (`HullCollider.carry`) и поворачиваются на изменение курса. Подпрыгнувший
переносится, пока он внутри габарита корабля (до 40 тиков) — корабль не уезжает из-под ног (ТЗ 12.3).
Покинувший корабль получает скорость палубы.

**Наклон.** При наклоне корпуса описанная коробка вертикального игрока в осях корпуса шире и тонет в палубе
на сантиметры; неглубокое (до 0,25 м) погружение сверху выталкивается. До 30° наклона сила тяжести действует
по нормали к палубе (сцепление, ТЗ 12.4), круче — скольжение. Оба эффекта найдены игровыми тестами.

**Анти-полёт.** Mixin в `ServerGamePacketListenerImpl.noBlocksAround`: игрок у деталей корабля не считается
«висящим в воздухе» (иначе выделенный сервер кикает через ~4 с).

**Реестр кораблей.** Поиск сущностей Minecraft не годится — корабль хранится в секции чанка по центру,
а игрок у кормы 245-метрового корабля в сотне блоков от неё. `ShipRegistry` держит загруженные корабли по мирам.

**GameTest.** Шаблон `ship_dock` 28×22×28 (раньше был `ship_bay` 17×14×17 — удалён вместе с `empty`):
каждый тест удаляет сущности в своей зоне при старте, и корабль, задевающий соседнюю зону, исчезал.
Фазы тестов отсчитываются по тикам корабля, а не по часам теста.

### Ограничения шага 2 (осознанные)

- ~~Нет «ступеньки» на детали корабля~~ — сделано в разд. 13 (ревью 2).
- Корабль не толкает сущности, в которые въезжает боком — проходит сквозь (пункт 9 прототипа).
- Детали с поворотом внутри корпуса (не осевые) пока учитываются по описанной коробке.
- Клиентская часть (свой игрок) автотестами не покрыта — GameTest работает только на сервере.

## 11. Подъёмная сила, повреждение камеры, земля (реализовано, шаги 3–4 прототипа)

**FlightModel** (`core/flight`) — полёт как целое, без Minecraft. За тик: газ (утечки, автоклапаны,
перегрев), пересборка массы при изменении > 50 г, затем 1 или 8 подшагов (8 — если рядом твёрдые блоки):
вес в центре масс; архимедова сила каждой камеры в центре газа (газ собирается у верха неполного мешка);
сопротивление; контакт; шаг `RigidBody`. Мир — через `Environment`/`ContactQuery`, в игре это
`physics/WorldEnvironment`.

**Камеры в чертеже** — `CellSlot` (отсек, коэффициент заполнения 0,9, масса оболочки 0,2 кг/м²).
**Присоединённая масса** — в `RigidBody` по осям корпуса: (0,1; 0,9; 0,9) × масса воздуха, вытесненного
камерами. У прототипа поперёк оси это ≈ 1,7 т при собственной массе 1,5 т.

**Контакт с миром.** (Снимок блоков на тик и контакт граней — разд. 13.) Точки на рёбрах деталей через ≤ 1 м
(у прототипа ≈ 1000). Вошедшая в блок точка
получает пружину с демпфером по нормали и трение (Кулон, сглаженный вязким около нуля). Суммарная
жёсткость задана на кг эффективной вертикальной массы (собственная + присоединённая) и делится между
касающимися точками: осадка = вес / (400·(m + m_прис)) при любом числе точек, явный интегратор устойчив.
У каркаса без камер это g/400 ≈ 2,5 см, у прототипа с пустыми камерами ≈ 1,1 см (сверено игровым тестом
в шаге 5: 13 734 Н / (400 · 3144 кг) = 1,09 см, измерено 1,09). Глубина ограничена 0,25 м — корабль, оказавшийся в земле,
выдавливается со скоростью ≤ 3,6 м/с, а не выстреливает. Нормаль блока берётся только с «открытых»
граней (сосед не полный блок) — точка в земле выталкивается вверх, а не вбок.

**Поведение (проверено тестами и сверено с ручным расчётом):** уравновешивание прототипа при 77,5 %
наполнения (масса 1500 кг); уравновешенный висит на любой высоте ниже высоты давления; наполнение 95 %
у земли → высота давления ≈ 450 м, дальше стравливание и подъём до ≈ 2,6 км, где корабль проскакивает
равновесие, тяжелеет и медленно снижается (как настоящий); утечка 1 %/с в носовой камере → −10° за 30 с;
крен: период ≈ 20 с, раскачка затухает; при посадке сила контакта = весу.

**Найдено при реализации.** Массы ферм в шаге 1 были завышены вчетверо (оценка 30–40 кг/м против
2,5–5 кг/м у цеппелинов) — исправлено. Маленький каркас 13×7×7 газ не поднимет даже с правильными
массами: подъёмная сила растёт как объём, масса каркаса — примерно как поверхность. Поэтому летающий
прототип крупнее.

**Стоимость.** ≈ 0,3–0,4 мс на тик для прототипа (ядро, без учёта обращений к блокам). Для LZ 129
понадобятся: точки контакта только с нижней стороны корпуса и только у блоков из быстрой отсечки
по секциям, а не по всему габариту; кэш состояний блоков на тик.

### Ограничения (осознанные)

- Масса стоящих на борту игроков и мобов не учитывается (ТЗ 8.3) — следующий кандидат.
- Газ всегда при температуре воздуха (+ перегрев, который пока никто не задаёт); ветер нулевой.
- Нет двигателей и рулей (фаза 3 по ТЗ 26) — горизонтально корабль двигают отладочные команды.
- Удар о землю не повреждает каркас — `StepReport.maxImpactSpeed` уже считается для будущей системы повреждений.
- Корабль не толкает сущности, в которые въезжает; блоки мира не ломает.

## 12. Строительство (реализовано, шаг 5 — фаза 1, пункты 1–2 прототипа)

**Ядро (`core/assembly`).** `AssemblyPlan` — монтажный план чертежа: каждая деталь и камера `ShipLayout` —
монтажная точка с предметом, этапом (ТЗ 5.4) и явным списком опор «что должно стоять до». Опоры заданы вручную,
а не выведены из геометрии: 20-метровая ферма касается и одного кольца, но держаться на нём не может. Тест сверяет,
что каждая опора физически примыкает к детали (зазор ≤ 15 см), и что проверка чувствительна (киль в 2 м под
мешком опорой не считается). План проверяется при создании: все детали покрыты, ссылки существуют, циклов нет.
Детали без опор стоят на стапеле — их нижние точки контакта и есть стапельные опоры площадки.
`ConstructionState` — прогресс: установка с отказами (не тот предмет, уже стоит, нет опор + список недостающих).
`AssemblyTargeting` — луч взгляда в осях корпуса против коробок неустановленных точек для предмета в руке
(`OrientedBox.rayHit`, метод плит); одно и то же считают клиент (подсветка) и сервер (установка).
`SiteCheck` — размещение и проверка площадки (ТЗ 4.2): низ корпуса на верхней грани блока, на который смотрят,
центр над ним, курс кратен 90°; проверка — высота мира, пересечение с другими кораблями, твёрдый блок под
каждой стапельной опорой (у прототипа 39 столбцов под тремя кольцами), свободный объём габарита.

**Игра.** Стройка — та же `AirshipEntity` в режиме «на стапеле»: физика заморожена, коллизия и рендер — только
установленные детали (`hullShapes()`, `visibleParts()`), прогресс — в NBT («Construction») и в синхронизируемых
данных. Поэтому хождение по собранному (ТЗ 5.5) работает без нового кода, а спуск (`launch()`) — это снятие режима:
тот же корабль начинает летать с сохранённым газом. Без заправки мешки пустые, корабль лежит на опорах
(заправка до спуска — AV-015, разд. 17).
`BlueprintTableBlock` выдаёт чертёж и сводку (окна выбора нет — модель одна). `BlueprintItem`: ПКМ — разместить
проект, Shift+ПКМ — ход работ или спуск. `ShipPartItem` (кольцо, киль, ферма, мешок): ПКМ → `ConstructionSites.tryInstall`
проверяет то, что требует мира, — блок между глазами и точкой (ТЗ 5.2 «перекрыт доступ»), блоки и живые сущности
в объёме детали; при успехе предмет расходуется (не в творческом), звук. Клиент: `BuildPreview` рисует контур
проекта (зелёный/красный, проблемный блок, нос), `AirshipRenderer` — «призраки» неустановленных деталей:
бледные в 8 м от игрока, голубые — куда можно поставить деталь из руки, зелёный/красный — выбранная взглядом.
Команды: `/airship build complete|launch`; команды полёта на стройку не действуют.

**Проверено.** Unit: план, порядок установки, выбор взглядом (в т.ч. повёрнутый корабль и «сквозь кольцо — мимо»),
площадка с числами ручного расчёта (габарит 90,25…110,75 при щелчке по x = 100; блок x = 90 мешает, x = 89 — нет;
верх ровно на y = 77 не мешает — нужен допуск на границе блоков). Игровые тесты: площадка в доке (помеха, яма под
кольцом, яма между кольцами), монтаж через настоящий предмет у игрока-заглушки (опоры, досягаемость, камень на линии
взгляда, камень и стойка в объёме киля, расход предметов), стойка проваливается сквозь пустое место киля и стоит на
установленном, сохранение стройки, стройка неподвижна, спуск: осадка 1,1 см, с 95 % газа — подъём 2,1 м за 2 с.

### Ограничения (осознанные)

- Стол — без окна выбора моделей (одна модель); чертёж — один предмет на тип корабля.
- Курс проекта только по сторонам света; площадка — один уровень под всеми кольцами.
- Пересечение проектов проверяется только с загруженными кораблями (`ShipRegistry`); `SavedData` с реестром
  кораблей появится вместе с выгрузкой чанков (ТЗ 22.9).
- Детали нельзя снять обратно (только `/airship remove` всей стройки); нет стапельных опор/лесов как объектов.
- Заправка камер — батареями баллонов (AV-015, разд. 17); полноценная инфраструктура — AV-024.
- Масса игроков учитывается после спуска (AV-014, разд. 16); корпус на стапеле неподвижен.

## 13. Ревью 2 (GPT) и наблюдения владельца — хождение по деталям, согласование с блоками, контакт

Владелец в игре: с Shift по каркасу не пройти и у края не остановиться; с поперечины кольца на настил (25 см)
приходится прыгать. GPT (коммит `9e04e6d`) прислал 7 замечаний — все подтвердились по коду, числа сверены.

**Столкновения сущностей (№1, ступенька).** `HullCollider.resolve`: детали всех кораблей обрезают смещение,
уже разрешённое ванилью; если что-то изменилось, итог снова проверяется блоками (`Entity.collideBoundingBox`),
и так до согласия, не больше 4 проходов, иначе сущность стоит. Причина: обрезка по осям повёрнутого корпуса
может увеличить мировую составляющую — в сценарии GPT (стена x = 1, корпус под 45°) игрок уходил в стену на 45 см.
В клине «стена + косая стенка» чередование проекций сходится лишь вдвое за проход, поэтому там сущность
останавливается (допустимое смещение и так ≤ 10 см). Выталкивание из палубы вверх (MAX_SINK) теперь тоже не
загоняет голову в блок. «Ступенька» как в ванили: стоящая сущность, упёршаяся в деталь по горизонтали,
поднимается не выше `maxUpStep`, проходит и опускается; берётся, если прошла дальше. Только в первом проходе —
если её срезал потолок, второй раз не пробуем.

**Shift (№4).** `Player.maybeBackOffFromEdge` до столкновений спрашивает `canFallAtLeast` → `Level.noCollision` —
только блоки. Mixin `PlayerMixin` дополняет ту же пробу деталями кораблей (`HullCollider.supports`, касание
гранью не в счёт). Только для своего игрока на клиенте, как и столкновения.

**Перенос (№2).** Смещение «палуба везёт» обрезается блоками мира (без своего корабля). Прижатого к блоку
палуба обгоняет — он теряет опору; сдавливание (урон) не моделируется.

**Загрузка (№3).** Сначала газ, балласт и окончательная масса, потом ориентация и скорости. Пересборка массы при
вращении добавляет ω × ΔЦМ — правильно в полёте, лишнее при загрузке (было +0,297 м/с при ω = 1 рад/с).

**Синхронизация мешков (№6).** На сервере хранится последнее *отправленное* наполнение, сравнение — с ним.
Раньше сравнивалось с прошлым замером, и утечка медленнее 0,002 за 5 тиков не доходила до клиентов никогда.

**Контакт с миром (№5, №7).** Раз в тик берётся снимок коробок блоков вокруг корабля ванильным обходом
(`Level.getBlockCollisions` — он видит формы выше своей клетки: забор, стена 1,5 блока) → `CollisionBoxes`
(разложены по клеткам 1 м). Все 8 подшагов контакта идут по снимку, без обращений к миру (раньше — по блоку на
каждую точку в каждом подшаге). Точки на рёбрах работают как раньше; для пар «форма детали — коробка блока»,
которые пересекаются, но ни одна точка этой формы в коробку не попала (блок под серединой грани киля),
добавляется контакт грани: к ближайшей открытой грани блока, глубина — лучами (`OrientedBox.rayHit`) через
область перекрытия, точка — среднее самых глубоких (у плоского касания — центр перекрытия). Касание гранью
(нулевой объём) — не контакт.

**Проверено.** Unit: сценарий GPT №1 дословно (старый путь даёт 0,55/0,55 — тест это проверяет), потолок над
выталкиванием, ступенька 0,25 / 0,75 / в воздухе / под потолком / на повёрнутом корабле, опора для Shift;
снимок блоков (верх забора, закрытые грани, сплошной массив); сценарий GPT №5 (было 0 точек, стало 1) и посадка
килем на рельс между его кромками: осадка 1,090 см = расчёт 13 734 Н / (400 · 3144 кг), 12 контактов, сила = весу.
Игровые: загрузка вращающегося корабля (ЦМ −0,296945, скорость 0), медленная утечка (в мешке 0,7703, клиенты
видят 0,7706), верх забора твёрд, перенос под блоком (голова доходит до блока и не входит), ступенька стойки
с пола на поперечину (−5,5) и с поперечины на киль (−5,25), опора палубы для Shift. Все пять игровых тестов
на найденные ошибки падают без исправлений (проверено откатом): скорость 0,29694 м/с, голова на 0,70 м в блоке,
ступенька застревает на −6,0 и −5,5, клиенты видят 0,8000, верх забора — пустота.

**Ошибка в этом исправлении (найдена владельцем в игре, 10.11.2026).** Проверка «сошлось» сравнивала итог
прохода с его началом, а не с результатом деталей. Обрезка деталью не идемпотентна: на наклонённом корпусе
повторная обрезка уже обрезанного смещения даёт новые крошечные отличия (перевод между осями). Проходы
не сходились, срабатывал запасной вариант «стоять» — **каждый тик, на любой детали**: по качающемуся в воздухе
или неровно лежащему кораблю ходить было нельзя. Исправлено: если блоки не меняют итог деталей — он годится,
готово. Все прежние тесты были на идеально ровных кораблях (а на полу дока корабль выравнивается в точный ноль),
поэтому ошибку не поймали. Тесты: `HullColliderTest.playerWalksOnSlightlyTiltedGroundedShip` (модель игрока
по тикам: было 0,2 м из 8, стало 8) и игровой `walkingOnSwayingFlyingShip` (дифферент −0,13°, крен 0,18°:
было 0,000 м, стало 4,35 м за 30 тиков). **Урок: ходьбу проверять на неровном корабле.**

### Ограничения (осознанные)

- Сдавливание между палубой и блоком не моделируется — прижатый проваливается сквозь палубу.
- В клине «блок + косая деталь» сущность останавливается, а не скользит к углу.
- Связка Shift ↔ mixin и ступенька своего игрока проверяются в игре: GameTest не двигает настоящего игрока
  (проверены стойки и сама проба опоры).
- Контакт грани — по 5 лучам на пару; узкий выступ между лучами наклонённой детали может остаться незамеченным.

## 14. Моторы и машинный телеграф (AV-011, фаза 3, ТЗ 8.4)

**Ядро.** `core/propulsion`: `Telegraph` — ступени full_astern … stop … full (доля мощности со знаком);
`EngineSpec` — мощность, статическая тяга, КПД винта, доля заднего хода, скорость раскрутки;
`Engine` — команда и фактическая доля мощности, которая тянется к команде (инерция мотора, ТЗ 8.5).
Тяга винта: T(v) = доля · min(T_стат, η·P/|v|), задний ход — × 0,5; тяга и мощность × ρ/ρ₀.
`core/structure/EngineMount` — мотор в чертеже: деталь-гондола, точка и ось тяги. `ShipLayout.engines()`.
`FlightModel`: моторы тикают раз в тик, тяга прикладывается в каждом подшаге в точке крепления вдоль оси винта,
по скорости набегающего потока в этой точке; от режима «нейтрально» не зависит. `setTelegraph(id|all, ступень)`.

**Прототип.** Две гондолы (2 × 1 × 1 м, 70 кг) у наружных граней боковых стоек среднего кольца, ось на y = −1,
z = ±6,5. Мотор: 18 кВт, 1500 Н на месте, η = 0,7, назад — половина, 0 → 100 % за 4 с. Монтаж — этап V,
опора — среднее кольцо; предмет «Моторная гондола».

**Игра.** Телеграф — командой `/airship telegraph <ступень> [мотор]` (пост управления — AV-013). Команда,
обороты сохраняются в NBT. Доли мощности синхронизируются клиентам (изменение > 1 %) — винты (две
деревянные лопасти, только вид) вращаются ≈ 3 об/с на полном ходу. `/airship info` показывает моторы.

**Числа (сверены).** Сопротивление вдоль оси с гондолами: Cd·S = 1,2 · 12 · 14 · 0,8 = 161,28 м². Полный ход:
3000 = ½ · 1,225 · 161,28 · v² → v = 5,511 м/с (unit: 5,5108). Полный назад: 1500 Н → 3,897 м/с. Один мотор:
момент 9750 Н·м против демпфирования вращения 38 945·ω² → ω = 0,50 рад/с. В доке за 4 с разгона: 2,928 м/с
и 4,26 м против численного 2,885 и 4,10 (разница — масса газа на высоте дока).

**Найдено при реализации.**
- Гондолы на кормовом кольце сдвигали ЦМ назад на ≈ 0,8 м — уравновешенный корабль садился на хвост и сползал
  (тесты «висит на месте» упали) → гондолы на среднем кольце.
- Ниже центра масс (как у цеппелинов) тяга давала бы ≈ 7° дифферента на полном ходу — без рулей высоты нельзя,
  поэтому ось винтов на высоте ЦМ. Остаток: ЦМ на 8 см ниже оси (−1,08) → дифферент 0,1–0,5° на нос
  и снижение ≈ 2,4 см/с на полном ходу.
- Игровой тест: корабль, сдвинутый кормой в барьерную стену дока, выталкивался контактом вперёд — неверная
  постановка теста, не физика.

### Ограничения (осознанные)

- Рулей нет: курс и высоту на ходу держать нечем (AV-012); на одном моторе корабль крутится.
- Поста управления нет — телеграф только командой (AV-013).
- Топлива, перегрева, износа и отказов (ТЗ 8.4) пока нет; «остановленный» мотор — ступень stop.
- Обдув винтом и аэродинамика гондол не учитываются; гондолы входят в сопротивление только через габарит.

## 15. Рули высоты и направления (AV-012, фаза 3, ТЗ 8.5)

**Ядро.** `core/structure/ControlSurface` — стабилизатор с рулём: деталь, руль направления или высоты, центр
давления, нормаль (направление силы при положительной команде), площадь. `ShipLayout.controlSurfaces()`.
`FlightModel.applySurfaces`: F = ½·ρ·V²·S·a·(τ·δ − α) по нормали в центре давления, V и α — по скорости
набегающего потока в этой точке (с вращением корпуса); a = 2,3 /рад, τ = 0,5, δ ≤ 25°, срыв при 0,35 рад; без
воздушной скорости — ноль; на заднем ходу руль не работает, стабилизатор — работает. Привод рулей — 15°/с.
Сопротивление корпуса оценивается по габариту **без** оперения (`ShipLayout.aeroSize`): стабилизаторы — несущие
плоскости со своей силой.

**Поперечная сила корпуса** (`HullDrag`, `liftAreaY/Z`): F = −½·ρ·C·S·|u|·v_поперёк, C = 0,5 /рад на
продуваемую площадь — оценка. Найдено тестом руля: без неё вираж держался только квадратичным сопротивлением
бортом, корабль скользил на 12° и поворачивал в 10 раз медленнее (0,008 рад/с).

**Прототип.** Верхний стабилизатор 3 × 2 м (12 кг) над верхней поперечиной кормового кольца — руль
направления; два боковых 3 × 3 м (18 кг) у боковых стоек — рули высоты. Монтаж — этап V, опора — кормовое
кольцо; предмет «Стабилизатор с рулём». Оперение тянет ЦМ назад (48 кг на x = −8,5) → **балансировочный
балласт**: 200 кг воды делятся нос/корма так, чтобы ЦМ был над серединой (125,5 / 74,5 кг) — `ShipLayouts`.

**Игра.** `/airship rudder <°>`, `/airship elevator <°>`; команды и отклонения сохраняются в NBT; `/airship info`.
Отклонение видно (AV-028): фактические углы рулей уходят клиенту в пакете моторов (`DATA_ENGINES`, «r»/«e», порог
0,5°); клиент доводит показ со скоростью рулевой машинки. Рендер рисует переднюю половину стабилизатора
неподвижной, заднюю — руль — повёрнутой на шарнире посередине хорды вокруг оси x̂ × n (задняя кромка уходит против
нормали силы).

**Пересмотр 10.11.2026 (жалоба владельца «слабо поворачивает», D-132).** τ = 0,7 (теория тонкого профиля для руля
в 50 % хорды; было 0,5), предел отклонения 30° (было 25°), наклон поперечной силы корпуса C = 1,0 (было 0,5).
Подбор перебором: τ 0,7 + 30° дают 2,5°/с, + C 1,0 — 3,2°/с; увеличение площади киля до 10 м² добавляло меньше
и потребовало бы менять геометрию. С пульта: руль ±30°, руль высоты ±20°.

**Снос в сторону (D-133).** Сопротивление корпуса прикладывалось в ЦМ. Человек не по оси сдвигает ЦМ вбок,
и плечи тяги бортовых моторов становятся разными: 1 м смещения 80 кг → ≈ 130 Н·м → разворот −19…−27° за минуту
полного хода. Теперь сопротивление и поперечная сила приложены на оси корпуса (середина габарита по x и z,
по высоте — у ЦМ, чтобы не менять подобранный дифферент D-114). Тест `personOffCentreDoesNotPullShipAside`:
курс 0,42° за минуту, без исправления −26,7°.

**Числа (сверены).**
- Уравновешивание при 0,879 (расчёт 1585,05 / (1,1397 · 1582,1) = 0,879), масса с газом 1704 кг,
  потолок по газу ≈ 1,32 км (пик 1331 м).
- Вираж на полном ходу с полным рулём: независимое решение равновесия сил и моментов.
  - Было (τ 0,5, 25°, C 0,5): ω = 0,0241 рад/с, скольжение 9,9°; модель — 0,0234.
  - Стало (τ 0,7, 30°, C 1,0, масса 1736 кг): при V = 5,533 м/с ω = 0,0565 рад/с (3,24°/с), скольжение 13,1°,
    радиус 98 м; модель — 0,0559.
- Один мотор, рули нейтрально: 0,48 рад/с (было 0,50 — оперение добавляет ≈ 440 Н·м демпфирования).
- Игровой тест разгона: 2,866 м/с и 4,15 м за 4 с против численных 2,824 и 4,00.

### Ограничения (осознанные)

- Поворот ≈ 3,2°/с на 5,5 м/с; на малом ходу медленнее (сила руля ~ V²).
- Один мотор руль не пересилит: моторы на плече 6,5 м, руль на 5,5 м/с даёт ≈ 0,5 кН·м против 9,75 кН·м.
- Корпус на ходу даёт поперечную силу без смещения центра давления (нет дестабилизирующего момента Манка).
- Коэффициенты (a, τ, C поперечной силы) — оценки; сверка с реальными данными — с обшивкой (фаза 5).

## 16. Штурвальный пост и люди на борту (AV-013, AV-014; ТЗ 8.3, 9.1–9.2)

### Штурвальный пост

- **Деталь плана.** `PrototypeShip.HELM` — 30 кг, коробка 0,6 × 1,1 × 0,8 м на носу настила киля
  (центр (9,6; −4,7; 0)); шаг монтажа `helm` (этап V, опора — киль), предмет `helm`. Масса сдвинула ЦМ вперёд —
  балансировочный балласт теперь 107,5 / 92,5 кг (D-118), сухая масса 1615 кг.
- **Сервер (`control/HelmService`).** Встать: корабль спущен, пост установлен, от глаз до коробки поста ≤ 4 м,
  у штурвала нет другого игрока, который ещё в мире и рядом. Команды (`apply`) принимаются только от стоящего
  у штурвала и только пока он рядом. Телеграф — ступень относительно первого мотора, всем моторам сразу
  (`Telegraph.step`). Балласт — по 10 кг на нажатие поровну из всех мешков. Отойти — рули и клапаны в ноль,
  телеграф остаётся. Каждый тик корабль проверяет стоящего: пропал из мира, умер или отошёл — пост свободен.
  Кто у штурвала, не сохраняется: после перезагрузки к штурвалу встают заново.
- **Сеть (`network/AirshipNetwork`).** Три пакета клиент → сервер: `take_helm`, `leave_helm`, `helm_input`
  (за тик: ступень телеграфа, рули, клапаны, сброс балласта). Обработка в главном потоке сервера; ID корабля
  ищется в мире игрока; чужие и недопустимые команды отбрасываются в `HelmService`.
- **Клиент (`client/HelmClient`).** ПКМ пустой рукой: луч от глаз до коробки поста в пределах досягаемости
  блока → `take_helm`, обычное действие отменяется. Пока игрок у штурвала (`DATA_HELM` — UUID строкой),
  `MovementInputUpdateEvent` забирает клавиши движения: W/S — по фронту нажатия, A/D, пробел/бег — пока
  держишь; ввод игрока обнуляется (не ходит, не прыгает, не приседает). Shift — `leave_helm`.
  Приборы — слой интерфейса `helm_hud` поверх всего; данные — `DATA_HUD` (сводка раз в 4 тика, пока пост занят).

### Люди на борту

- `FlightModel.Payload(local, massKg)` — точечные массы в осях корпуса; входят в массу, ЦМ и инерцию
  (`buildMass`, `currentMassKg`) и в уравновешивание `weighOff`.
- `AirshipEntity.updatePayload` раз в 10 тиков: живые сущности (не наблюдатели), у которых под ступнями деталь
  этого корабля (`HullCollider.supports` по полоске −0,15…+0,05 м у низа коробки). Масса: игрок 80 кг, остальные —
  80 · объём коробки / 0,648 (объём коробки игрока), в пределах 5…3000 кг. Точка — ступни.
- Пересборка массы — только если сумма изменилась больше чем на 0,5 кг или момент — больше чем на 20 кг·м:
  шаг человека по палубе не пересчитывает инерцию каждые полсекунды.

### Найдено

- `weighOff` не учитывал людей на борту: уравновешенный «при людях» корабль был тяжелее расчёта
  (unit-тест `peopleAtTheBowPitchShipNoseDown`).
- `dropBallast("all", 10)` берёт из мешков по порядку — с поста всё уходило бы из носового и сбивало дифферент.
  Пост сбрасывает поровну (игровой тест `helmTakesCommandsAndReleases`: без исправления 97,5 / 92,5 кг вместо
  102,5 / 87,5).

### Ограничения (осознанные)

- Пост — коробка временного рендера; модели штурвала и рычагов нет (AV-023).
- Телеграф с поста — один на оба мотора; раздельное управление моторами — командой `/airship telegraph … engine_port`.
- Масса людей — по коробке сущности, а не по «настоящей» массе моба; предметы и блоки на борту массы не дают.
- Игрок у штурвала стоит на месте сам: его не привязывает к посту ничего, кроме обнулённого ввода; толчок
  или наклон палубы могут увести его дальше 4 м — пост освободится.
- Клиент шлёт `helm_input` каждый тик, пока игрок у штурвала (20 маленьких пакетов в секунду).

## 17. Заправка камер (AV-015, первый этап; ТЗ 5.4, 7.3–7.4)

**Ядро.** `core/physics/GasFilling.transfer` переносит минимум из запаса, расхода за шаг и свободной
вместимости при текущих давлении/температуре камеры. Запас и расход — в молях; стандартный м³ определён
как 101325 Па, 288,15 К. `FlightModel.supplyGas` выбирает атмосферу по мировой высоте центра камеры и сразу
пересчитывает массу. Пустая камера принимает любой из двух газов; непустая — только свой. Открытый ручной
клапан запрещает подачу; утечка не запрещает заправку, но продолжает терять газ.

**Предмет и взаимодействие.** `gas/GasSupplyItem` — батареи водорода и гелия, по 200 стандартных м³,
расход 10 стандартных м³/с. Остаток хранится в `DataComponents.CUSTOM_DATA` (`AirshipGasMol`); отсутствие поля
означает новый полный предмет, явный ноль — пустой. Расходуется и в Creative. `GasSupplyService` каждый
серверный тик использования проверяет живого игрока, предмет в используемой руке, взгляд, досягаемость,
блоки и детали на пути. Источник теряет ровно количество, принятое камерой. При потере цели подача прекращается;
после ревью Claude (AUD-04-02) прицел нужен только для подключения: штуцер запоминается («шланг»,
`GasSupplyService.HOSES`), дальше каждый тик проверяются только досягаемость + 1 м и блоки между глазами и
штуцером — качка корабля в воздухе не обрывает подачу.

`CellSlot.fillingPort` — коробка 30 см под серединой отсека, всегда доступная с технического прохода даже
при сложенном под потолком мешке. `AirshipRenderer` рисует голубую метку; собственной твёрдой коллизии и
добавочной массы у штуцера нет (включён в оборудование камеры). Выбор работает в повернутой системе корабля.
Shift+ПКМ предметом переключает ручной клапан выбранной камеры один раз за нажатие. Предмет остаётся в режиме использования до отпускания ПКМ, подавляя автоповтор Minecraft; режим клапана фиксируется на старте в AirshipValveUse у игрока. Отпускание Shift при удержанной ПКМ не запускает заправку, следующее использование заново задаёт режим. Штурвал (клавиша V) открывает и закрывает клапаны всех
камер только по смене состояния клавиши и при уходе закрывает лишь то, что открыл сам (AUD-04-01:
раньше каждый тик «закрыто» с поста перебивало клапан штуцера); прибор показывает, открыт ли хотя бы один клапан.

**Стапель и сохранение.** На стапеле `FlightModel.tickGas` обновляет газ без интегрирования корпуса;
наполнение и утечки синхронизируются раз в 5 тиков, как в полёте. Спуск сохраняет газ и повреждения.
NBT камеры дополнен `ManualValve`; отсутствие в старом сохранении означает закрытый клапан. Газ и тип
уже сохранялись в `Mol`/`Gas`. Подача не сохраняется отдельным соединением и после загрузки сама не возобновляется.

**Числа.** За секунду: n = 101325·10/(8,314462618·288,15) = 422,925433799 моль;
водород весит 0,852617675 кг. Тест предмета на сервере дал 422,925433799 моль, 0,852617675 кг и остаток
8035,583242188 моль. Источник + камера = 8458,508675987 моль. Для стапеля проверяется
n(t) = n₀·exp(−(0,02 + 0,01)·t) при утечке 2 %/с и открытом клапане 1 %/с.

**Ограничения.** Это переносная подача прототипа: нет производства/рецептов/заправки батарей, станций,
шлангов и смешивания газов (AV-024). Объём и расход оборудования — временные игровые параметры.
Значки — 16×16 в стиле Minecraft (`tools/textures/make_textures.py`, D-130). Реальная мышь, вид штуцеров и анимация мешка
в клиенте требуют проверки владельцем; серверные тесты этого не подтверждают.

## 18. Корабль и выгрузка чанков, реестр кораблей (AV-017; ТЗ 22.9)

- **Правило (ядро, `core/world/ChunkKeeping`).** Экипаж — игрок, стоящий на деталях корабля (тот же опрос, что
  и масса людей, раз в 10 тиков), или стоящий у штурвала. Пока экипаж есть и ещё 1200 тиков (60 с) после
  ухода, корабль держит чанки под габаритом с запасом 2 м и по ходу на 2 с (габарит, сдвинутый на v·2 с).
  После загрузки мира отсчёт начинается «экипажа нет». Стройка ничего не держит.
- **Тикеты (`world/ShipChunks`).** `TicketController` «airshipvoyage:airship», владелец — UUID корабля,
  тикеты тикающие. Набор пересчитывается раз в 10 тиков: лишние снимаются, новые ставятся. Снимаются все при
  удалении сущности из мира (выгрузка, удаление, смена измерения). При загрузке мира callback снимает все
  тикеты контроллера: висящих после выключения сервера «вечных» чанков нет.
- **Пауза над незагруженной землёй.** Перед шагом физики: все чанки под габаритом (+1 м) должны быть загружены
  (`Level.hasChunk`), иначе шаг пропускается. Скорость не трогается, корабль продолжит, когда земля появится.
  Без этого корпус, свисающий за край загруженной области, «не видел» бы блоки и при загрузке оказался бы
  внутри них.
- **Реестр (`world/ShipRecords`, SavedData `airshipvoyage_ships`).** UUID, модель, место (до 0,1 м), игровое
  время последнего обновления, стройка или нет. Обновляется при появлении в мире, раз в 100 тиков и при
  выгрузке. Запись удаляется, если корабль уничтожен или ушёл в другое измерение. Сама сущность по-прежнему
  сохраняется в своём чанке; реестр — указатель для `/airship list`.

### Ограничения (осознанные)

- Корабль без экипажа, ушедший за край загруженной области (например, на телеграфе), замирает — так
  разрешает ТЗ 22.9 для первой версии. Отдельной симуляции выгруженных кораблей нет.
- Тикеты держат ровно габарит; игроку на борту чанки вокруг грузит сам Minecraft (дальность прорисовки).
  Для LZ 129 (245 м) это проверить отдельно.
- Реестр не восстанавливает корабль, если файл чанка потерян: это указатель, не вторая копия.

## 19. Дифферент перекачкой балласта (AV-027; ТЗ 8.3, 9.1)

- `FlightModel.transferBallast(from, to, kg)` — масса неизменна, ЦМ смещается; приёмный мешок — не больше 200 кг.
  `endBallast(bow)` — мешок у носа/кормы по координате x.
- Пост: стрелки ↑/↓ (клавиши `trim_up`/`trim_down`, переназначаются) — насос 5 кг/с, нос вверх — вода из носового
  мешка в кормовой. Пакет `helm_input` теперь несёт флаги (газ, сброс, дифферент вверх/вниз) одним числом:
  у `StreamCodec.composite` в 1.21.1 не больше 6 полей.
- Приборы: дифферент в градусах и балласт нос/корма.
- Зачем: руль высоты на 20 км/ч почти бессилен (+30° меняет дифферент рулевого на носу с −9,1° лишь до −6,6°),
  а перекачка 40 кг выравнивает до −1,4° (тест `trimmingBallastLevelsShipWithHelmsmanAtTheBow`).
